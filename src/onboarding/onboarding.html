Step 1 — Local IPFS (Kubo) node

Content is served from your own Kubo node. Install IPFS Desktop (easiest) or run kubo directly. The extension only needs the subdomain gateway at http://localhost:8080.

Troubleshooting
  • Confirm the gateway is reachable: curl -I http://bafkqaaa.ipfs.localhost:8080/ — should return 200 OK.
  • If that returns 301 to the path gateway, your Kubo is configured without the subdomain gateway. In IPFS Desktop, toggle the experimental subdomain gateway, or set Gateway.PublicGateways."localhost".UseSubdomains = true in ~/.ipfs/config and restart.
  • Cross-origin: the browser treats each <cid>.ipfs.localhost as its own origin, so Kubo's API Origin allowlist doesn't apply to the content path we use.

Step 2 — Ethereum execution RPC

Provide a mainnet execution RPC URL. It doesn't need to be trusted: Helios verifies every state read against the consensus-committed state root.

About the permission prompt you're about to see

Chrome will ask you to grant access to two hosts:

    Chrome's wording is "Read and change your data on [host]". That phrase is Chrome's generic template for any host permission — it looks the same whether an extension reads one JSON field or fully takes over a page. It does not reflect what this extension actually does.

    What this extension actually does with that permission:

    • Reads Ethereum state via JSON-RPC (eth_call, eth_getBlockByNumber, etc.) to resolve ENS names.
    • Reads beacon-chain light-client updates from the consensus RPC so Helios can verify that state.
    • Never sends transactions, never touches wallet accounts, never uploads anything.

    Source is on GitHub — the RPC calls are in src/lib/resolver.ts and the consensus fetch in src/offscreen/offscreen.ts.
